# Will

В основе Will — передача воли от человека, близкого к некоторому благу, другому,
чтобы помочь ему этого блага достичь.

Will — клиент-серверное приложение для работы тренера (ведущего) и ученика.
Тренер даёт поручения и составляет тренировки с упражнениями, рабочими весами,
повторениями и паузами отдыха; ученик выполняет их подход за подходом,
отчитывается о сделанном, а тренер проверяет результат. Сервер хранит всё
состояние в SQLite и общается с терминальными клиентами по gRPC.

![Два клиента Will: первый участник пишет в своей комнате и принимает второго в мир](docs/terminal.svg)

## Как это устроено

- **Ведение и послушание** — любой участник может попросить другого стать его
  тренером. Когда тот соглашается, между ними создаётся связь и общая рабочая
  комната (у тренера она называется `Ведение`, у ученика — `Послушание`). Один и
  тот же человек может быть учеником для одних и тренером для других.
- **Задания и тренировки** — сообщение тренера в рабочей комнате становится
  заданием, которое числится за учеником, пока тот не отчитается о выполнении
  (`/done`). Для тренировок (`/train`) задаются упражнения, веса, повторения и
  время отдыха между подходами. Ученик может проходить подходы по одному
  (`/begin`, `/end`, `/finish`), отмечать, насколько тяжело дался подход (`!`,
  `!!`), и оставлять заметки к упражнениям (`/remark`). Когда тренер заходит в
  комнату, выполненное задание отмечается просмотренным.
- **Личное пространство и комнаты** — у каждого участника своё пространство с
  личной комнатой (`Слово`) и рабочими комнатами. Хозяин сам решает, кого
  впустить (`/admit`) и кому какие комнаты открывать в зависимости от близости
  (`acquaintance`, `neighbour`, `friend`).
- **Вход через существующих участников** — каждое устройство идентифицируется
  своим токеном. Первый человек в новом мире входит сразу, а каждого следующего
  принимает в мир кто-то из уже существующих участников.

Внутри кода предметная область описана собственной системой понятий; словарь
терминов кода и интерфейса собран в [GLOSSARY.md](GLOSSARY.md), а устройство
сервера и баз данных — в [ARCHITECTURE.md](ARCHITECTURE.md). Английская версия
этого документа — в [README.md](README.md).

## Сборка

Понадобятся [xmake](https://xmake.io), компилятор C++20 (GCC 10+, Clang 12+ или
аналог) и пакеты разработки SQLite3 и gRPC/Protobuf (`libgrpc++-dev`,
`libprotobuf-dev`, `protobuf-compiler`, `protobuf-compiler-grpc`). Библиотеку
[CLI11](https://github.com/CLIUtils/CLI11) xmake скачивает автоматически.

В Debian/Ubuntu:

```bash
sudo apt install build-essential xmake libsqlite3-dev \
  libgrpc++-dev libprotobuf-dev protobuf-compiler protobuf-compiler-grpc
```

Сборка:

```bash
xmake
```

Бинарные файлы появятся в `build/`:

| Файл | Назначение |
|------|------------|
| `will-server` | gRPC-сервер, хранящий состояние мира в SQLite |
| `will-client` | Интерактивный терминальный клиент |
| `will-load-clients` | Генератор нагрузки (конкурентные сессии и сообщения) |

## Быстрый старт

Запустим сервер, подключим двух участников и проведём первую тренировку.

**Терминал 1 — сервер:**

```bash
./build/will-server
```

В текущем каталоге создаются три файла базы данных: `will.eternity.db`,
`will.space.db` и `will.time.db`. Чтобы сбросить состояние и начать с нуля,
достаточно остановить сервер и удалить эти три файла.

**Терминал 2 — первый участник:**

```bash
./build/will-client --host 127.0.0.1 --port 7770
```

При первом запуске клиент сохраняет токен в файл `will.device_token` и входит на
сервер. Поскольку база пуста, первый участник создаётся сразу и получает имя и
личную комнату `Слово`. Обычный текст в комнате отправляется как сообщение;
`/help` выводит список команд, `Ctrl+D` закрывает клиент.

**Терминал 3 — второй участник:**

```bash
./build/will-client --device-token-path will.device_token.user2
```

Второй клиент подключается и ждёт подтверждения от уже существующего участника,
показывая свой номер (`#2`).

**Подтверждение входа (в терминале 2):**

```text
/birth            посмотреть список ожидающих входа (виден номер #2)
/bear 2           принять участника под номером 2
```

Теперь оба участника в системе и уже добавлены в списки контактов друг друга.

**Связь тренера и ученика и первая тренировка:**

В терминале 3 попросите первого участника стать вашим тренером:

```text
/helm             перейти к управлению контактами и комнатами
/dwellers         посмотреть имя первого участника
/ask <имя_тренера>
```

В терминале 2 примите запрос, перейдите в появившуюся комнату `Ведение` и
назначьте тренировку:

```text
/helm
/accept <имя_ученика>
/rooms
/room 2           войти в комнату «Ведение — <имя_ученика>»
/train День жима | жим лёжа 60x10 1:30/70x8 | отжимания 0x12
```

В терминале 3 откройте комнату `Послушание` и выполните тренировку:

```text
/rooms
/room 2           войти в комнату «Послушание — <имя_тренера>»
/begin 1 1 1      начать 1-й подход 1-го упражнения тренировки №1
/finish 1 60x10
/done 1 Сделано | жим лёжа 60x10 70x8 | отжимания 0x12
```

Как подключиться к открытому демонстрационному серверу, описано в
[REFERENCE.md](REFERENCE.md#visiting-the-public-world).

## Структура проекта

```text
src/
  domain/    доменная модель: сущности, значения, записи, порты хранения, отказы
  infra/     SQLite-адаптеры (три базы данных), gRPC-контракт (messenger.proto)
  server/    will-server: сессии, привязка протокола к домену, жизненный цикл
  client/    will-client: транспорт, команды, терминальный интерфейс
tests/       юнит-, компонентные, процессные и интеграционные gRPC-тесты
packaging/   сборка Debian-пакета, служба systemd, скрипты развёртывания
```

## Тесты

```bash

xmake test
```

Тесты на doctest проверяют логику домена, сохранение и восстановление из SQLite

## Токены и безопасность

Токен устройства (`will.device_token`) — единственный ключ к учётной записи: он
хранится в открытом виде у клиента и в базе сервера, и при потере файла
восстановить профиль нельзя. Удаление файла токена не удаляет профиль с сервера,
а лишь создаёт новый при следующем запуске. Для работы под несколькими профилями
на одной машине указывайте `--device-token-path`. Одновременно у одного токена
может быть только одна активная сессия — новое подключение закрывает предыдущее.

По умолчанию в локальной разработке gRPC работает без шифрования; при запуске
сервера в сети включайте TLS (`--tls-cert`, `--tls-key`, `--no-plain`).
